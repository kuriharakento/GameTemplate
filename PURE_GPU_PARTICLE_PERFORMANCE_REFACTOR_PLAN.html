Pure GPU Particle
性能問題 修正計画書

10万粒子で顕在化する最大容量全走査、単一CounterへのAtomic競合、未使用Event生成、GPU Eventの最悪O(N²)探索を解消し、フレーム負荷を「最大容量」ではなく「実Alive数＋実Spawn数＋実Event数」に比例させるための実装計画です。

対象: KentoCompoEngine / GameTemplate　作成日: 2026-08-12

2. GPU Eventsで花火を作れるか

作れます。親EmitterのDeath Eventを、爆発用の子Emitterへ接続します。

打ち上げEmitter→弾Particleが上昇→寿命終了→Death Event→爆発Emitter→火花を放射
auto* rocket = effect->GetEmitter(0);
auto* burst  = effect->GetEmitter(1);

burst->SetGPUEventSourceEmitterIndex(0);
burst->SetGPUEventTrigger(1);               // Death
burst->SetGPUEventProbability(1.0f);
burst->SetGPUEventVelocityInheritance(true, 0.2f);
burst->SetGPUEventInheritColor(true);
burst->BindGPUEventSource(rocket);

さらに爆発EmitterのDeath Eventを煙Emitterへ接続すれば、打ち上げ→爆発→残煙という連鎖もCPU Readbackなしで作れます。ただし現在のEvent探索は大量イベント時にスケールしないため、本計画のEvent再設計を先に行います。

3. 現状の問題と根拠

ID問題現在の処理量影響優先度
P-01particleCount_=maxParticlesとしてSimulation/Convertを全容量DispatchO(Capacity) × 2 pass以上Aliveが少なくても10万slot走査最高
P-02Spawn要求が1以上だと全Dead slotが単一spawnCounterへAtomic Add最悪O(Dead Capacity)の単一点競合少量Spawnでも大容量Poolで急落最高
P-03購読者がいなくても全Spawn/Death EventをAtomic AppendO(Spawn+Death)不要なAtomicとBuffer書込み高
P-04子SpawnごとにSource Eventを先頭から線形検索最悪O(ChildSpawn × SourceEvents)花火の大量爆発で破綻最高
P-05透明Spriteの面積・重なりを制限しないO(covered pixels × overdraw)Computeが軽くてもPixel Shaderが飽和高
P-06全SimulatorがEvent/Ribbon用大容量Bufferを持つO(Capacity) VRAMSpriteだけでも不要VRAMを確保中

重要: 現在はPure GPUではありますが、「実Alive数だけ処理するGPU駆動構成」ではありません。CPU Readbackを除去したことと、GPU上の計算量が最適であることは別問題です。

4.7 SpawnとUpdateを分離した際の意味論

現行Shaderは新規Spawn後、同じDispatch内でUpdate Moduleまで評価します。修正後も見た目を維持するため、SpawnをAliveListCurrentへ追加した後にUpdate Argsを構築し、新規Particleを同フレームのAliveUpdateへ含めます。

  • Rate SpawnごとにbirthOffsetInFrameを生成し、一時Spawn MetadataまたはParticleの予約fieldへ保存する。
  • 新規Rate ParticleのUpdateはeffectiveDt = max(0, frameDt - birthOffsetInFrame)を使用する。既存AliveとBurst/Event Spawnは仕様で定めた各effectiveDtを使用する。
  • Age、位置積分、時間依存Module、Curve/LUT評価は同じeffectiveDtと補正後Ageを一貫して使用する。
  • Initial ModuleとSpawnShapeはSpawn CSで一度だけ評価する。
  • Update Moduleは既存Aliveと新規Spawnの両方へ同じフレームに一度だけ評価する。
  • Update中に死亡したParticleはNext Alive Listへ入れずFree Listへ戻す。
  • Update終了後のAliveListNextだけをConvert/Draw対象にする。

4.8 Emitter間GPU Event構造

現行:
Source EventBuffer
  └─ Childの各Spawn threadが先頭から線形探索
       → ChildSpawn × SourceEvents

修正後:
Source Update
  └─ EventBuffer（購読bitがあるtypeだけ）
       ▼
Child EventFilter [1 thread / source event]
  └─ FilteredEventIndices[]
       ▼
Child SpawnPrepare = Event/Burst/Rateを別rangeとして割当
       ▼
Child Spawn [1 thread / accepted event]
  └─ FilteredEventIndices[eventOffset + eventSpawnId]を直接参照

複数の子Emitterが異なるtrigger/probabilityを持つため、Filtered Listは接続edge単位で所有します。Source Event Bufferを子ごとに複製しません。GPU Event接続は同一ParticleEffectインスタンス内に限定し、Effectを跨ぐ接続はEditor/API/JSON Loadの全経路で拒否します。

D3D12用語: 本書の「DispatchIndirect」は処理概念の略称です。D3D12 APIとしてはD3D12_INDIRECT_ARGUMENT_TYPE_DISPATCHを持つCommand Signatureを作成し、ID3D12GraphicsCommandList::ExecuteIndirect()でCompute Dispatchを発行します。

List更新方法

// Update CS: 1 thread = AliveList[current]の1要素
uint particleIndex = AliveListCurrent[dispatchId];
Particle p = ParticlePool[particleIndex];
Update(p);

if (p.alive) {
    uint dst = AtomicAppend(AliveCounterNext);
    AliveListNext[dst] = particleIndex;
} else {
    PushFreeList(particleIndex);
    EmitDeathEventIfRequested(p);
}

Ping-Pongすることで、同一フレーム内に読むAlive Listと書くAlive Listを分離し、順序競合を防ぎます。

7. GPU Event再設計

購読情報を事前計算

ParticleEffectが同一Effectインスタンス内のEmitter接続グラフを構築し、sourceごとに必要なEvent bitを設定します。Effectを跨ぐ接続は許可しません。

EventWriteMask:
bit 0 = Spawnに購読者あり
bit 1 = Deathに購読者あり
bit 2 = Collisionに購読者あり（将来）

購読者がないEventはCounter Atomicもpayload書込みも行いません。

線形Filterを1回だけ実行

// 1 thread = 1 source event
if (event.type == requestedType &&
    Random(event.particleId) <= probability) {
    uint dst = AtomicAppend(filteredCount);
    if (dst < filteredCapacity)
        FilteredEventIndices[dst] = sourceIndex;
    else
        AtomicIncrement(filteredOverflowDropCount);
}

子EmitterのEvent Spawn threadはFilteredEventIndices[eventOffset + eventSpawnId]を直接参照します。Filtered capacityは接続edgeごとにmin(SourceEventCapacity, EdgeEventSpawnLimit)とし、CounterをcapacityへClampして後段へ渡します。

Spawn発生源と容量不足時の優先順位

Spawn要求は合算した曖昧な範囲にせず、Event、Burst、Rateの3レンジと3 Dispatch Argsへ分離します。Free slotはEvent→Burst→Rateの順で割り当て、継続生成のRateを最初にdropします。

free = FreeCounterSnapshot;
acceptedEvent = min(requestedEvent, free); free -= acceptedEvent;
acceptedBurst = min(requestedBurst, free); free -= acceptedBurst;
acceptedRate  = min(requestedRate,  free);

dropEvent = requestedEvent - acceptedEvent;
dropBurst = requestedBurst - acceptedBurst;
dropRate  = requestedRate  - acceptedRate;

各Dispatchは独立したthread ID空間を持つため、Event由来だけが位置・速度・色継承を適用します。

Emitter依存順序

  • 同一フレームEventを使う場合、単一Effect内のEmitter graphをトポロジカル順にDispatchします。
  • 循環参照はEditor/API/JSON Load時に検出します。
  • 循環を許可する場合は明示的なPreviousFrameモードだけとし、Event BufferをPing-Pongします。
  • source削除・差し替え時はdescriptorをFence安全に更新します。
  • 別Effectインスタンスをsourceとして渡すAPI呼び出しは失敗を返し、参照を保持しません。
仕様決定: 初期実装では循環Event接続とEffect間Event接続を拒否します。暗黙の1フレーム遅延や外部Effect lifetime依存は導入しません。

8. 実装Phase

0

基準計測とGPU Pass可視化

  • Simulation、Spawn Prepare、Module、Convert、Event Filter、Ribbon、Particle Drawを個別timestamp化
  • Alive/Capacity/Spawn/Event/covered-pixel proxyをCSV出力
  • Sprite 10k/50k/100k、Mesh、Ribbon、Bloom On/OffをRelease 1080pで計測

完了条件: 改修前baselineを同一GPU・同一scene・300 sampleで保存し、ボトルネックをpass単位で説明できる。

1

Event無効化とO(N²)探索除去

  • Event write maskを追加
  • 購読者なしEventのAtomic/writeを完全skip
  • edge単位Filtered Event Index Buffer、容量式、overflow drop counterを追加
  • 子Spawnをindex直接参照へ変更
  • 同一Effect内の依存graphと循環検出を追加し、Effect間接続を拒否

完了条件: Event未使用EffectでEvent write 0。10万Source Eventでも処理量が線形で、花火連鎖が同一seedで再現し、capacity超過時もBuffer外書込み0。

2

Free ListによるSpawn

  • 初期化CSでFree Listへ0..capacity-1を構築
  • Event/Burst/Rateを別range・別Dispatch Argsとして生成
  • Event→Burst→Rateの優先順でFree slotを予約
  • 各Spawn threadがFree Listから1 indexをPop
  • 発生源別Drop counterをGPUで更新
  • 死亡時はindexをFree ListへPush

完了条件: Spawn 100／Capacity 100kでAtomic回数がO(100)となり、全Dead slot走査を行わない。容量不足時の継承先とdrop優先順が仕様通り。

3

Alive ListとSimulation DispatchIndirect

  • Alive ListをPing-Pong化
  • フレーム冒頭のResetFrameCounters CSでNext counterを明示reset
  • Args Build CSでAlive数からUpdate Dispatch Argsを生成
  • Update CSをParticle index入力へ変更
  • 新規Spawnのbirth offsetとeffectiveDtを一貫適用
  • Survivor append、Death free push、Event emitを統合
  • 診断値を専用Snapshot Ringへ複製して生Counterから分離
  • Loop reset/Clear時のList/Counter初期化をGPU化

完了条件: Capacity 1,000,000／Alive 10,000のSimulation時間がCapacity 100,000／Alive 10,000と±10%以内。Ping-Pong resetと遅延診断が互いを上書きしない。

4

Convert・Draw・RibbonのAlive List化

  • ConvertをSurvivor数だけDispatchIndirect
  • Render BufferはAlive順で連続出力
  • Draw ArgsをAlive Counterから生成
  • Ribbon prefix/sort入力をAlive Ribbon粒子だけに限定
  • Sprite/MeshではRibbon専用Bufferを遅延確保

完了条件: Sprite/MeshのConvertがO(Alive)、Ribbon sort capacityが実Aliveに近い2の累乗となる。

5

Pixel/Overdraw対策

  • Particle draw timestampとBloom Mask drawを分離
  • Screen-size culling、透明度0、極小粒子をConvertで除外
  • 任意のSoft Particle/Depth cullingを追加
  • Emitterごとの最大screen size、distance culling、LOD spawn倍率を追加
  • Bloom Maskの1/2解像度を品質設定として比較

完了条件: Compute改善後も重いsceneについて、Pixel負荷を数値で特定し、LOD High/Medium/Lowが期待通り負荷を削減する。

6

耐久・互換・ドキュメント

  • 容量変更、Renderer交換、Scene遷移、Pool再利用を各100回
  • D3D12 Debug Layer、GPU-based validation、Debug/Release

12. リスクと対策

List重複・欠落

Atomic append/popの境界バグは描画欠落や二重更新を生みます。Debug専用GPU validation passでAlive+Free=Capacity、index一意性を検証します。

Counter resetと診断世代

ResetFrameCounters CSをフレーム冒頭へ固定します。診断はframe ID付きSnapshot Ringへ複製し、生Counterの再利用後に読むことを禁止します。

Event依存と寿命

同一フレームeventは単一Effect内のtopological orderを必須とし、循環とEffect間接続を拒否してdangling sourceを防ぎます。

Filtered Event overflow

edge単位capacityを明示し、全Appendを境界検査します。超過はdrop counterへ記録し、Counterをcapacity以下へClampします。

DispatchIndirect

Arguments Bufferのoffset、alignment、stateを型付きhelperへ集約し、各passで重複実装しません。

再現性と既存の見た目

Thread順依存を避けParticle serial/Event IDで決定論化します。旧乱数列とのbit一致は要求せず、既存JSON corpusの統計的同等性をPF-15で要求します。

Overdraw誤認

Compute最適化だけで完了扱いにせず、Particle Draw/Mask Drawを別timestampで測定します。

13. 他AI・設計レビュー用チェック項目

レビュー担当には、実装の好みではなく次の整合性を確認してもらいます。

  1. Spawn→Update→Convertの順序で、新規Spawnが同フレームにちょうど一度だけUpdateされるか。
  2. Rate由来の新規Spawnが全時間依存処理でframeDtではなくframeDt - birthOffsetInFrameを使い、AgeとModule評価が同じ時間基準か。
  3. Alive ListとFree Listの和集合がフレーム安定点で全Particle indexと一致し、重複しないか。
  4. ResetFrameCounters CSがNext counterだけを0にし、Current/Freeを壊さず、swap後の旧Currentを次フレーム冒頭で確実にresetするか。
  5. 診断snapshotが生Counterではなくframe ID付きRingからFence完了後に読まれるか。
  6. Counter 0、Capacity不足、全死亡、全生成の境界でunsigned underflow/overflowがないか。
  7. Args Build後のUAV→INDIRECT_ARGUMENT transitionと、再生成前の逆transitionが全経路にあるか。
  8. 同一フレームEventのEmitter dispatch順がtopological orderで保証されるか。
  9. 複数の子Emitterが同じSource Eventを異なる条件で読む場合、edge単位Filtered Listで正しく分離されるか。
  10. Event/Burst/Rateが別range・別Argsで、容量不足時にEvent→Burst→Rateの優先順となり、Event継承が他の発生源へ漏れないか。
  11. FilteredEventIndicesの全Appendがcapacity検査され、overflow Counterと後段Clampが一致するか。
  12. Effect間接続がAPI/Editor/JSONの全入口で拒否され、dangling pointer/descriptorを残さないか。
  13. Event未購読時にEvent Counter Atomic、payload write、Filter Dispatchが本当に0になるか。
  14. Ribbonのsort対象がCapacityではなく実Alive Ribbon数になっているか。
  15. 通常フレームに診断目的のCounter Readbackが紛れ込まないか。
  16. 透明ParticleのPixel負荷をCompute改善結果と混同していないか。

レビュー時に明示すべき確定事項

  • GPU Event循環とEffect間Event接続は初期実装では拒否する。
  • 新規Spawnは同フレームUpdate対象とし、Rate SpawnはeffectiveDt=frameDt-birthOffsetを使用する。
  • Spawn容量の優先順位はEvent→Burst→Rateとする。
  • Alive/Free/Event/ArgsはCPUへ同期Readbackせず、診断は専用Snapshot Ringから非同期取得する。
  • Filtered Event Listは接続edge単位で、容量はmin(SourceEventCapacity, EdgeEventSpawnLimit)とする。
  • 既存公開APIとJSONは原則互換を維持する。
  • RNGの旧実装とのbit一致は要求せず、既存JSONの統計的同等性を要求する。
  • Particle payload indexは寿命中固定し、描画順だけRender Bufferでcompactする。

14. Definition of Done

  • Spawn、Simulation、Convertの処理量が最大容量ではなく実Spawn/Alive数に比例する。
  • Dead slot全体による単一Spawn Counter競合が存在しない。
  • Event/Burst/Rateは別Dispatch rangeで処理され、容量不足時の優先順位がEvent→Burst→Rateとなる。
  • ResetFrameCounters CS、Alive List swap、次フレームresetの順序が明示され、診断はFence管理された専用Snapshot Ringから取得される。
  • GPU Event未使用時はEvent Atomic・書込み・Filter Dispatchがすべて0である。
  • Event Spawnに子Spawn×Source Eventの二重ループが存在しない。
  • FilteredEventIndicesはedge単位容量を超えて書かず、overflowを正確にdrop計上する。
  • GPU Event接続は同一Effectインスタンス内だけに限定され、Effect間接続と循環接続を全入口で拒否する。
  • 花火のRocket→Burst→SmokeがGPU内で動き、位置・速度・色継承と決定論的再生が成立する。
  • Rate Spawnのbirth offsetがAge、移動、時間依存Moduleのすべてへ一貫して反映される。
  • 通常フレームのParticle/Counter/Event/Draw Arguments CPU Readbackが0である。
  • Sprite/Mesh/RibbonとSelective Bloomの既存JSONについて、構造・機能が回帰せず、乱数由来の見た目が定義済み統計許容範囲を満たす。
  • PF-01～PF-16と性能予算をすべて満たす。
  • Debug/Release、D3D12 Debug Layer/GPU-based validationでWarning/Error/Corruptionが0である。
  • 容量変更、Effect破棄、Pool再利用後にresource/descriptorが基準値へ戻る。
推奨実装順: Phase 0 → 1（Event）→ 2（Free List）→ 3（Alive List）→ 4（Convert/Ribbon）→ 5（Overdraw）の順です。各Phaseを個別に計測・回帰確認し、複数の根本変更を一度に混ぜません。
